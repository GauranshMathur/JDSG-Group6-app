# Architecture review — 18 August 2026

One of a series; the index and the status of every finding below live in
[`README.md`](README.md).

Taken against `main` at 42981ac, after milestones 8 through 8.7. It looks at **module
depth** — how much behaviour sits behind each interface, and where knowledge has ended up
with no module to own it. It is not a bug hunt, though three defects fell out of it.

Vocabulary is deliberate and used throughout: a **module** is anything with an interface
and an implementation; its **interface** is everything a caller must know to use it
correctly, not just the signature; a module is **deep** when a lot of behaviour sits behind
a small interface and **shallow** when the interface is nearly as complex as what is behind
it; a **seam** is a place where behaviour can be altered without editing in that place;
**locality** is change and knowledge concentrating in one place; **leverage** is capability
per unit of interface a caller has to learn.

## Measured, not inferred

Three numbers were taken with throwaway specs, which were removed afterwards. Nothing in
`web/` was changed to produce them.

| What | Result |
| --- | --- |
| Queries per page, 1 row → 20 rows, tag and search | **4 → 42** |
| Queries per page, 1 row → 20 rows, feed | 4 → 4 |
| `GET /posts?page=-1` and `/@user?page=-1` | **`ArgumentError`** — a 500 on two routes |
| Specs that reach any of the three `rate_limit` declarations | **0** |

## Candidates

Ordered by strength of recommendation, not by size.

---

### 1. Give "load a post for rendering" a module — **Strong**

**Files.** `post.rb:36`, `ranked_feed.rb:221`, `profile_feed.rb:21,25`,
`posts_controller.rb:24,25`, `tags_controller.rb:8`, `search_controller.rb:10`,
`replies_controller.rb:13`.

The chain `.includes(user: { avatar_attachment: :blob }, images_attachments: :blob)` is
written out five times. It is missing from `tags_controller.rb:8` and
`search_controller.rb:10`, and `replies_controller.rb:13` has a drifted copy that
eager-loads the author but not the attachments.

The two pages missing it are exactly the two pages with no query-budget spec — there is a
`feed_query_budget_spec.rb` and a `profile_query_budget_spec.rb`, and no tag or search
equivalent. The absent module and the absent guard line up, which is why the N+1 has been
sitting there unnoticed: **42 queries to render twenty rows**, against the feed's 4.

**Problem.** How to load a post for rendering is knowledge with no module, so three of
eight call sites do not have it.

**Solution.** A `Post.for_rendering` scope that `timeline` composes. Every site names it
instead of respelling it.

**Wins.** Tag and search shed 38 queries. Locality: one place decides preloading. Leverage:
one scope, eight call sites. One query-budget spec covers every timeline instead of two.
Deletion test: delete it and the complexity reappears eightfold — it earns its keep.

### 2. `Post.search` depends on the adapter — **Strong**

**Files.** `post.rb:37`, `user.rb:24,27`, `spec/requests/search_spec.rb:18`.

Two scopes that look symmetric:

```ruby
# user.rb:24 — portable
scope :search, ->(query) { where("username LIKE ?", "%#{sanitize_sql_like(query.downcase)}%") }

# post.rb:37 — not portable
scope :search, ->(query) { where("posts.body LIKE ?", "%#{sanitize_sql_like(query)}%") }
```

`User.search` downcases the query, and `username` is normalised lowercase on write
(`user.rb:27`), so both sides of the comparison are folded and the match is the same on any
adapter. `Post.search` folds neither, and post bodies are stored verbatim. It works today
because SQLite's `LIKE` is case-insensitive for ASCII. PostgreSQL's `LIKE` is
case-sensitive.

So `search_spec.rb:18` — "is case-insensitive", green today — passes because of which
database is running, not because of anything the code does.

**Three documents currently say otherwise.** `REQUIREMENTS.md` F-6.3 records "Search
behaves identically on SQLite and PostgreSQL" as **Met**;
[ADR 0004](adr/0004-hashtags-and-search.md) claims the same; `CLAUDE.md` forbids depending
on adapter-specific behaviour. This is not a reason to reopen ADR 0004 — its decision, a
plain `LIKE` rather than a search engine, still holds. It is the claim of *parity* that is
untrue. Since the PostgreSQL switch is owed work and blocks the latency measurements
(N-6.7), this lands the day that switch is attempted.

**Solution.** Fold case inside the scope, as `User.search` already does, and give both
scopes a model spec — neither has one today, which is why the asymmetry is invisible.

**Wins.** Search survives the PostgreSQL switch. F-6.3 becomes true rather than
aspirational. Testable without an HTTP request.

### 3. `Rails.cache` is a global with no seam — **Strong**

**Files.** `ranked_feed.rb` (8 references), `config/environments/test.rb:23`,
`sessions_controller.rb:4`, `passwords_controller.rb:4`, `registrations_controller.rb:5`,
`spec/services/*.rb`.

One missing seam produces two unrelated failures.

**The ranked feed's internals became its interface.** `RankedFeed` declares five methods.
Four spec files depend on `CACHE_KEY`, `REBUILD_LOCK_KEY`, the `{cutoff:, entries:}` payload
schema, the lock protocol, and in one case the Marshal byte size
(`page_cost_spec.rb:40–53`, `window_spec.rb:25–28`). Those are the effective interface, and
nothing declares them. Changing the cached shape breaks four spec files rather than none.
Because the only seam is a process-wide global, five spec files each carry the same six-line
`around` hook swapping `Rails.cache` by hand.

**The rate limiter is inert under test.** `config/environments/test.rb:23` sets
`:null_store`. `rate_limit` is backed by `Rails.cache`. Three limits are declared — sign-in,
registration, password reset — and `grep` finds **zero** specs that reach one. As tested,
the brute-force protection on sign-in is indistinguishable from three comments.

**Solution.** Take the store, and the clock, as parameters. Tests pass a real in-memory
adapter instead of disabling the subsystem. Two adapters justify the seam: the real store in
production, an in-memory one in tests.

**Bears on [ADR 0010](adr/0010-stored-rank-score.md) without deciding it.** That record
leaves open "whether `RankedFeed` survives as a class". Naming this seam first makes the
stored-score experiment a swap behind an interface rather than a rewrite through four spec
files. It is also the shared-cache change `CLAUDE.md` already owes the infrastructure track.

**Wins.** Rate limiting becomes testable. The payload shape stops being public. Five
duplicated `around` hooks collapse into one. The warm and stale paths become reachable —
today every request spec exercises only the cold rebuild.

### 4. Nothing owns "a page of a timeline" — **Strong**

**Files.** `posts_controller.rb:15,40–43`, `profiles_controller.rb:9`,
`timeline_pagination.rb`, `ranked_feed.rb:22,32`, `profile_feed.rb:2,13`,
`posts/index.html.erb:25`, `profiles/show.html.erb:34`, `posts/_pagination.html.erb`,
`posts/_post.html.erb:54`.

`RankedFeed` and `ProfileFeed` have the same shape — `new(…, page:)`, `#items`,
`#next_page` — and no shared interface, so every caller rebuilds the same assembly around
them. Both controllers carry the identical expression:

```ruby
RankedFeed.new(page: (params[:page].to_i if params[:page].present?) || 0)
```

Nothing validates it. `page=-1` reaches `entries.drop(-20)`, which raises `ArgumentError` —
**a 500 on the feed and on every profile**. The duplicated assembly duplicated its defect.

The rest of the spread:

- `PAGE_SIZE = 20` is declared three times, under three names the specs have already forked
  on (`TimelinePagination::PAGE_SIZE`, `ProfileFeed::PAGE_SIZE`, `RankedFeed::PAGE_SIZE`).
- Three different "is there a next page?" protocols — a lookahead flag, and two variants of
  `size == PAGE_SIZE`.
- Two URL dialects. `_pagination.html.erb` takes a cursor and is used by tags and search;
  the feed and profiles hand-roll a `page=N` link and bypass it. Different label, different
  CSS class, different query parameter.
- `posts#create`'s failure path (`:40–43`) omits `@liked_post_ids` / `@reposted_post_ids`
  entirely, which is why `_post.html.erb:54` carries a defensive
  `defined?(liked_post_ids) && liked_post_ids&.include?(...)`. The guard exists to paper
  over an interface that callers satisfy inconsistently — one caller passes `Set.new` as a
  placeholder.

`TimelinePagination` is tangled into this. It is two modules under one name: a cursor half
used by 2 of its 5 includers, and an engagement-preloading half used by all 5. Its own
comment says it is "shared by every page that renders one — the feed, profiles, and later
the tag pages", and the feed and profiles both stopped using the half it is named after.

**Solution.** One `Timeline` interface returning a page that carries its items, its next
link, and the viewer's engagement. The page parameter is parsed in one place, so it is
rejected in one place. `TimelinePagination`'s two halves come apart on the way.

**Touches [ADR 0002](adr/0002-keyset-pagination.md) and
[ADR 0011](adr/0011-ranked-window.md) without reopening either.** ADR 0011 accepted
positional paging for the ranked feed; ADR 0002 keeps keyset elsewhere. Both stay true. What
is missing is a module that knows which applies where, instead of four views each knowing
separately.

**Wins.** Two 500s fixed in one place. One `PAGE_SIZE`, one next-page protocol. Deletes a
defensive view guard. Leverage: four timelines, one interface.

### 5. `ProfileFeed` still materialises the whole archive — **Strong**

**Files.** `profile_feed.rb:19–43`, `spec/requests/profile_query_budget_spec.rb`.

```ruby
posts   = @user.posts.top_level…to_a      # no LIMIT
reposts = @user.reposts…to_a              # no LIMIT
feed.sort_by { … }.drop(@page * PAGE_SIZE).first(PAGE_SIZE)
```

Every post the account has ever written, plus every repost, loaded into Ruby and sorted, to
return twenty rows. This is precisely the pathology N-6.8 removed from the ranked feed —
`ranked_feed.rb:108–114` records it at 763 ms — surviving untouched in the sibling service.
`docs/stress-testing.md:110` already measures 63 ms for an 873-post account.

The guard beside it cannot see this. `profile_query_budget_spec.rb` asserts a constant
*query count*, and the query count genuinely is constant: it would pass at twenty posts and
at two hundred thousand. The guard measures the axis that does not grow.

**Solution.** Order and limit in SQL, as the ranked archive already does. Give the budget
spec a rows-read assertion so the shape cannot regress.

**Composes with [ADR 0011](adr/0011-ranked-window.md); contradicts nothing.** That record
says profiles "never had a window and still do not" — a decision about *ranking*. A profile
is chronological; it needs no window, only a `LIMIT`.

**Wins.** Cost tracks the page rather than the account's history. Heavy accounts stop being
the slow pages. `FeedItem`'s `sort_time` and `score` lose their only writer — the file
already documents them as "read by nothing that renders one".

### 6. Invalidation does not know what the ranking knows — **Strong**

**Files.** `ranked_feed.rb:185,191`, `post.rb:21–22`, `like.rb:7–8`, `repost.rb:7–8`.

The ranking reads only what is inside the window and only `top_level` posts. `bust_cache` is
bounded by neither:

- A **reply** busts the ordering. `top_level` guarantees a reply can never appear in it.
- A **like on a post outside the window** busts the ordering. It cannot move anything.

Both force a rebuild that produces a byte-identical result. Rebuild rate is the quantity
milestone 8.6 was about, and it is being driven by events the ranking is defined to ignore.

The reverse gap exists too: `Post` declares `after_create_commit` and
`after_destroy_commit` but **no `after_update_commit`**, so editing a post's body never
busts the feed cache — though `after_save :sync_tags` does re-sync its tags on the same
write.

**Solution.** Move the window predicate behind one interface both sides call. The read side
already has it; the write side asserts nothing.

**Wins.** Locality: one window, both sides. Replies stop busting the feed. Edits stop being
missed. Testable without rendering a page.

### 7. The image policy lives in a view; the model's copy is dead — **Strong**

**Files.** `post.rb:100–102`, `posts/_post.html.erb:40`, `user.rb:57–63`,
`shared/_avatar.html.erb:5`, `spec/models/post_images_spec.rb:49`,
`spec/models/user_avatar_spec.rb:33`.

`Post#image_variants` defines the WebP conversion and EXIF stripping. Its only caller is its
own spec — `_post.html.erb:40` re-inlines the identical variant specification rather than
calling it. So a privacy rule is implemented in a template, and the module meant to own it
is kept alive by its test. `User` does the same thing correctly eight files away:
`avatar_thumbnail` is defined on the model and called from the partial.

F-7.3 (WebP) and F-7.4 (EXIF stripping) are both recorded as **Met**. What the specs assert
is `expect(variant).to be_present` — true of any lazily-built variant — and
`expect(user).to respond_to(:avatar_thumbnail)`. Neither processes an image or inspects its
output. Note also that stripping happens on *variant* generation, so the original blob keeps
its metadata and is reachable by its own Active Storage route, while F-7.4 is worded "on
upload".

The content-type allow-list is written four times: `post.rb:4`, `user.rb:46`,
`_composer.html.erb:24`, `profiles/edit.html.erb:20`. Adding a format is a five-place edit
with no compiler help.

**Solution.** Make the view call `image_variants`. Assert the produced format and the
absence of metadata rather than the existence of a method.

**Wins.** One place decides image policy. F-7.3 and F-7.4 gain real evidence. Posts match
the shape `User` already uses.

### 8. Like and Repost are one module, written twice — **Worth exploring**

**Files.** `like.rb` / `repost.rb`, `likes_controller.rb` / `reposts_controller.rb`,
`_like_button.html.erb` / `_repost_button.html.erb`, and both pairs of turbo-stream
templates.

Twelve files. The diff between `like.rb` and `repost.rb` is the class name. The diff between
the two controllers is the identifiers. The two button partials differ in an HTML entity and
a counter name. A third engagement type costs six more files.

Deletion test: deleting either side halves one concept rather than removing one — the
duplication is the concept being expressed twice.

**Judgement.** The duplication is stable and this is a proof of concept, so it is not
urgent. Worth doing when a third engagement type appears, or alongside candidate 6, which
edits the same three models.

### 9. One rule, several implementations — **Worth exploring**

| Rule | Written where | Risk |
| --- | --- | --- |
| tags are lowercase | `tag.rb:5` (`normalizes`), `post.rb:122`, `application_helper.rb:5`, `tags_controller.rb:7` | four copies; only one also strips whitespace |
| what a username is | `user.rb:3` — `/\A[a-z0-9_]{3,20}\z/`; `routes.rb:28` — `/[A-Za-z0-9_]+/` | two definitions disagreeing on case and length |
| the ranking formula | `ranked_feed.rb:203–207`; `script/scaling-curve:39–42` | a comment is the only thing binding them |

Each rule gets one home and the others call it. The formula is the cheapest of the three:
one spec that runs both and compares turns a comment into a gate.

## Where to start

**Candidate 1** is the recommendation. It is the only one carrying a measurement rather than
an argument, it has already produced a drifted sixth call site, and one scope retires five
copies while letting a single query-budget spec cover every timeline.

Then, depending on what matters most:

- **Most urgent** — candidate 2. Search breaks on the day of the PostgreSQL switch, and that
  switch is owed work that also blocks the latency measurements.
- **Most user-visible** — candidate 4. Two live 500s reachable by typing a URL.
- **Cheapest** — candidate 9. One spec turns a comment into a gate.

Candidates 3 and 5 are the two that change what the test suite is capable of proving:
3 makes the rate limiter and the warm cache path reachable at all, and 5 makes the profile
budget spec measure the axis that actually grows.

## What this review did not do

No code was changed. The three measurements came from throwaway specs that were deleted
immediately; `git status` on `web/` is clean apart from a stray `.DS_Store`.

Nothing here reopens an accepted decision. Where a candidate touches an ADR — 0002 and 0011
in candidate 4, 0011 in candidate 5, 0010 in candidate 3, 0004 in candidate 2 — the ADR's
decision still stands; what is being questioned is a gap the record did not cover, or in
candidate 2's case a claim of parity that turns out not to hold.
